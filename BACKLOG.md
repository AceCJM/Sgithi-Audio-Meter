## Medium-term features

- **Virtual audio cables.** Voicemeeter's signature feature — creating/destroying PipeWire `null-sink` "virtual cable" devices on demand from the UI. Explicitly out of scope for v1 (confirmed with the user during planning); v1 only controls/routes what already exists. Would need module load/unload management and probably persistence across restarts.
- **Patchbay pan/zoom.** Canvas is currently a fixed-size `DrawingArea` in a `ScrolledWindow`; a `GestureZoom`/scroll-to-zoom controller would help once real multi-device graphs get visually crowded.
- ~~**Better auto-layout.**~~ Fixed (2026-09-16): the actual bug behind the overlap confirmed in the near-term click-testing pass above wasn't the column heuristic itself, but `CanvasModel::sync()`'s per-column placement cursor being a local `[MARGIN; 3]` re-zeroed on every call - harmless if the whole graph synced once, but PipeWire discovers nodes one at a time, so in practice every node after a column's first landed at that column's starting y, stacking exactly on top of each other. Moved the cursor to a persistent `CanvasModel::next_column_y` field; verified with a regression test (`incremental_sync_does_not_stack_nodes_in_the_same_column`, added alongside a `batched_sync_matches_incremental_sync` sanity check) and visually in an isolated instance. The column heuristic itself is still just a first guess and may still want revisiting for large graphs.
- **libadwaita styling.** Currently plain `gtk::HeaderBar`/`gtk::Stack` to minimize dependencies. Swapping to `AdwApplicationWindow`/`AdwViewSwitcher` for GNOME-native styling is an isolated change to `src/ui/app.rs` plus the `libadwaita-1-dev` apt package.
- **Per-channel / balance control.** A strip's fader currently sets every channel to the same value. No balance/pan control for multi-channel devices.

## Standing lessons (not features, but worth keeping visible)

- **Never call `enum_params` with an unbounded count (`u32::MAX`)** against a live PipeWire/WirePlumber session. Early hardware-volume (`Device`/`Route`) work did exactly this and left the user's real `wireplumber` process stuck at 100% CPU system-wide, requiring a service restart to recover. The current code bounds these calls (8 for Node `Props`, 32 for Device `Route`); keep that pattern for any new param-enumeration code, and be cautious re-testing PipeWire-touching changes repeatedly against a live session — a CPU watchdog on `wireplumber` alongside any test launch is cheap insurance.
- **A registry global's initial `props` (from the `global`/`global_remove` listener) is not the same set as a bound object's full `info().props()`.** `card.profile.device` - needed to link a hardware Node to its `Device` Route (see `device_route.rs`) - is present in a Node's `info` event but *absent* from its registry `global` event props, even though `device.id` (the other half of that link) is present in both. This caused a real, silent bug: `route_link` was always `None`, so every hardware node fell back to reading its own (non-authoritative, sometimes stale) `Props`, and looked approximately-but-not-exactly right on screen - close enough to pass a casual visual check, wrong when cross-checked against `wpctl`. Any future code reading a property from a `GlobalObject`'s `props` should verify that property is actually present there (`pw-dump`'s output is `info().props()`-shaped and does *not* prove a key is in the registry global props) rather than assuming; if it isn't, get it from an `.info()` listener on the bound object instead, as `registry.rs`'s Node arm now does.
- **Programmatically updating a GTK widget that has a `connect_*` signal handler attached can re-emit that signal**, which for this app's fader/mute controls means silently sending a real `SetVolume`/`SetMute` command for a change the user never made - not just a display bug, a write-back into the user's real audio state. `Strip::update()` (called on *every* graph event, not just ones relevant to that strip) now blocks the relevant `SignalHandlerId` around each programmatic `set_value`/`set_active` call; any new widget in this app that both displays incoming state and accepts user input needs the same treatment.
- **A `pipewire::stream::Stream` you create is itself a regular registry `Node` - if your own registry listener doesn't know to ignore it, it will discover its own metering/probe streams as if they were application audio.** Building peak metering (`pw::peak`) this way created a real feedback loop live: each `Strip`'s metering stream registered as a `Stream/Input/Audio` node, `ApplicationsPage` gave *that* its own `Strip`, which started metering *it*, exponentially - caught within seconds via dozens of phantom "app streams" and the app process (not `wireplumber`) pegging a CPU core. Also: the `name` argument to `StreamRc::new`/`pw_stream_new` does **not** become the resulting node's `node.name` (that defaults to the whole process's name) - you must set `PW_KEY_NODE_NAME` explicitly in the stream's properties if `registry.rs` needs to filter your stream out by name, as `pw::peak::STREAM_NAME_PREFIX` now does.
- **Routing a high-frequency PipeWire event through the same full-page `sync()` used for occasional ones (volume/mute/rename) doesn't scale.** `sync()` reconciles every strip's placement, name, volume and mute state - fine for a user-driven change, but `Event::PeakLevel` alone arrives at ~30Hz *per watched node*, and even with only half a dozen strips on screen, running a full `sync()` for every tick pegged a CPU core (confirmed: dropped from ~130% to ~15% total after fixing). A frequent, narrowly-scoped event should update just the one widget it affects (see `ui::app`'s event loop special-casing `PeakLevel` to `Strip::set_peak`/`*Page::update_peak` instead of `sync()`) rather than reusing the general reconcile path.
- **A GTK widget attached with `set_parent()` (rather than added to a container via `append`/`add`) isn't detached just because its parent gets torn down or removed from *its* own parent.** `Strip`'s rename/category popover is `set_parent()`ed to the pencil button, so when a strip's nodes get removed and recreated (confirmed live: switching the Scarlett Solo's PipeWire profile, which drops/recreates all its nodes), dropping the old `Strip` finalized the pencil button while the popover was still attached - logged by GTK as "Finalizing GtkButton... but it still has children left" for every torn-down strip. Fixed by having `Strip`'s `Drop` explicitly call `self.edit_popover.unparent()`. Any future widget built with `set_parent()` instead of a container method needs the same explicit unparent in whatever teardown path drops it.
